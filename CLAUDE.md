# Quizzler

A Windows tray app that quizzes the user on software engineering (C# first) using spaced repetition.
Questions are authored as JSON in `content/`, mostly generated by Claude, and verified automatically.

## Layout

```
src/Quizzler.Core        Models, grading, SM-2 scheduler, session planning, QuizService (the study loop
                         every front end shares). No UI, no database.
src/Quizzler.CodeRunner  Roslyn: compiles + runs C# snippets; ContentVerifier checks predict-output and
                         predict-result answer keys.
src/Quizzler.Data        SQLite store (QuizDatabase implements Core's IQuizStore). Imported questions,
                         cards (progress), review log, flags, settings. Migrations via PRAGMA user_version.
                         SqlSandbox: runs a predict-result question's setup + query in in-memory SQLite, and works
                         out which setup rows affect the result (delete each in a savepoint, re-run, compare).
                         Used by the verifier, the CLI quiz and the app (SqlTableView draws the grids).
src/Quizzler.Cli         `quizzler` command: quiz, stats, validate, import, flags, settings.
src/Quizzler.App         WPF tray app (net10.0-windows): tray icon with due-count badge, reminder
                         notifications, quiz window, start with Windows. Ships content/ and auto-imports it.
tests/Quizzler.Tests     Unit + integration tests, and ContentBankTests (validates and executes content/).
content/<area>/<topic>.json   The question bank (source of truth for questions).
schema/questions.schema.json  JSON Schema for content files (editor validation/autocomplete).
tools/                   install.ps1 / uninstall.ps1 (per-user install), make-icon.ps1 (regenerates the .ico).
```

### App architecture

- `App.xaml.cs`: lifetime. Single instance per database (`SingleInstance`); a second launch signals the
  first to open its window. A 1-minute `DispatcherTimer` calls `Refresh()`: due counts → tray badge/tooltip,
  and `NotificationPolicy.ShouldNotify` (Core, unit-tested) decides on reminders.
- `--background` = tray only (used by the Run-key startup entry). `--db <path>` = alternate database.
- `QuizViewModel` wraps Core's `StudySession` (which holds all the session logic and is unit-tested);
  `QuizWindow` is XAML + keyboard shortcuts only.
- `StartupRegistration`: HKCU Run key. **Dev builds (running from bin\Debug|Release) never touch it
  automatically**; only an installed copy enables it on first run.
- `BundledContent`: imports content shipped next to the exe when its fingerprint changes.
- Notifications (`Services/Notifiers.cs`): `ToastNotifier` uses the Windows App SDK (`Microsoft.WindowsAppSDK.Foundation`,
  bundled self-contained, so no runtime install) for toasts with "Start quiz" / "Snooze 1 hour" buttons.
  Falls back to `BalloonNotifier` (H.NotifyIcon tray balloons) if the SDK can't initialise. Button clicks
  arrive on a background thread → marshalled to the dispatcher. A click while the app isn't running launches
  it; `ToastNotifier.GetLaunchAction()` reads which button. `--unregister-notifications` removes the registration.
- Theming (`Services/ThemeService.cs`): System/Light/Dark. Sets `Application.ThemeMode` (Fluent) and swaps
  `Themes/Light.xaml` ↔ `Themes/Dark.xaml`. **App colours must be referenced with `DynamicResource`**, and every
  key must exist in both files. Code blocks recolour via `CodeHighlighting` (a dark copy of AvalonEdit's C# scheme).
- Pack URIs must be assembly-qualified (`pack://application:,,,/Quizzler.App;component/...`).
- Settings window (`SettingsWindow` + `SettingsViewModel`): theme (live preview, Cancel reverts), study and
  notification settings, start with Windows. Theme is stored in the `settings` table under key `theme`.
- Log: `%LOCALAPPDATA%\Quizzler\quizzler.log`.

### Testing the app yourself

**Never launch the app's windows on the user's desktop.** A process started from the foreground app gets
keyboard focus even with `ShowActivated=false`, so the user's typing lands in the quiz (this happened: it
recorded their keystrokes as answers and triggered shortcuts). Safe options:
- Logic: unit-test `StudySession`, `NotificationPolicy`, etc. in Core.
- Visuals: render off-screen. Build a scratch harness that references Quizzler.App, does `new App()` +
  `InitializeComponent()`, applies a theme, builds the window with a scratch-DB view model, detaches
  `window.Content`, measures/arranges and renders it with `RenderTargetBitmap`. **Never pump the dispatcher
  in the harness**: `Application`'s constructor queues `OnStartup`, which would start the real app against the
  user's real database (also happened).
- Background-only checks (`--background --db <scratch>`) show no window; read the log for notifications.
- If a visible run is unavoidable, ask the user first. Use `--db <scratch>` and `--no-activate`.
Don't capture the whole screen; it may contain the user's private windows.

## Commands

```
dotnet test                                   # everything
dotnet test --filter ContentBankTests         # just the question bank
dotnet run --project src/Quizzler.Cli -- validate   # validate + run snippets, readable report
dotnet run --project src/Quizzler.Cli -- import     # validate, then import into the user's database
dotnet run --project src/Quizzler.Cli -- quiz       # study in the terminal
dotnet run --project src/Quizzler.Cli -- stats
dotnet run --project src/Quizzler.Cli -- flags      # questions the user flagged as wrong/unclear
dotnet run --project src/Quizzler.App               # the tray app (dev build)
powershell -ExecutionPolicy Bypass -File tools/install.ps1   # install/update to %LOCALAPPDATA%\Programs\Quizzler
```

After adding questions, the user re-runs `tools/install.ps1`; the installed app imports the new content on launch.

All database commands take `--db <path>`; default is `$QUIZZLER_DB`, then `%LOCALAPPDATA%\Quizzler\quizzler.db`.
**When testing the CLI yourself, always pass `--db` with a scratch path. Never touch the user's real database.**

## Data rules

- content/ JSON is the source of truth for questions; the database holds a copy (imported) plus progress.
- Questions missing from content on import are *retired*, not deleted, so progress returns if they come back.
- Editing a question keeps its progress (same id). If an edit changes the *meaning* of a question, give it
  a new id instead and delete the old one, so stale progress doesn't carry over.
- Journal mode is the SQLite default (not WAL) so the single .db file is always complete and safe to copy.
- Timestamps are stored as UTC Unix milliseconds. Schema changes = append a script in Migrations.cs.

## Fixing flagged questions

When asked to fix flags: run `quizzler flags`, find each id in content/, fix it, run `quizzler validate`,
then `quizzler import`, then `quizzler flags --resolve <id>` for each fixed question.

## Learning model (important context when writing questions)

- Every question is first asked as **multiple choice** (answer + 3 random distractors, shuffled).
- Once answered correctly, it's asked as **typed recall** next time (no options shown).
- A wrong answer in either mode drops it back to multiple choice; SM-2 sets the intervals.
- So every question must work in BOTH modes: the distractors must be plausible, AND the answer must be
  something a person could reasonably type (or the question is marked `"recall": "self"`).

# Question authoring guide

Follow this exactly when generating questions. After writing, ALWAYS run
`dotnet test --filter ContentBankTests` and fix every failure before finishing.

## File format

One file per topic: `content/<area>/<topic>.json`, e.g. `content/csharp/linq.json`. Add to an existing
file if the topic exists. New files start with:

```json
{
  "$schema": "../../schema/questions.schema.json",
  "questions": [ ... ]
}
```

## Fields

| Field | Required | Notes |
|---|---|---|
| `id` | yes | `<area>-<topic>-NNNN`, e.g. `cs-linq-0007`. Continue numbering from the highest existing id in that topic. **Never change or reuse an id**: the user's progress is keyed on it. |
| `type` | yes | `concept`, `predict-output`, `pick-the-code` or `predict-result` (see below). |
| `topic` | yes | Matches the file path: `csharp/linq`. |
| `difficulty` | yes | 1-5, see scale below. |
| `tags` | recommended | Lowercase, hyphenated: `["linq", "deferred-execution"]`. |
| `prompt` | yes | The question. Markdown inline code with backticks is fine. |
| `code` | predict-output, predict-result (optional otherwise) | C# shown with the prompt, or the SQL query for predict-result. |
| `setup` | predict-result only | SQL that creates and fills the tables. Shown to the user as grids. |
| `expect` | predict-result only, optional | `"row-count"` when the answer is just the number of rows; `"table-access"` for how the query plan reads a table; default is the rows. |
| `planTable` | table-access only, optional | Which table the plan question is about, as named in the plan (its alias). Needed for multi-table queries. |
| `answer` | yes | The single canonical correct answer. |
| `accepted` | optional | Other typed forms that should count as correct: abbreviations, synonyms. Case, whitespace, surrounding backticks/quotes, trailing `.` and trailing `()` are already ignored, so don't list those variants. |
| `distractors` | yes | 3 is ideal (2-5 allowed). Up to 3 are shown at random. |
| `explanation` | yes | 1-3 sentences: why the answer is right, and why the most tempting wrong answer is wrong. |
| `recall` | optional | `"self"` when the answer can't be graded by text match (see below). |

Area prefixes for ids: `cs` = csharp, `dotnet` = runtime/BCL/tooling, `design` = SOLID/patterns,
`dsa` = data structures & algorithms, `sql`, `web`, `git`. Add new ones as needed and list them here.

## Question types

### `concept`
A factual question with a **short** answer. Exact-graded answers must be ≤ 60 characters. Aim for a term,
keyword, type name, or Big-O, e.g. `sealed`, `Boxing`, `O(log n)`, `Liskov Substitution Principle`.
- If the natural answer is a sentence (an "explain the difference" question), set `"recall": "self"`.
  In typed mode the user writes their attempt, sees the answer, and grades themselves.
- Prefer phrasing that has one defensible answer. "Which keyword..." beats "What's a good way to...".

### `predict-output`
`code` is a complete C# program written as **top-level statements**: what does it print?
- These usings are implicit; don't write them: `System`, `System.Collections.Generic`, `System.IO`,
  `System.Linq`, `System.Text`, `System.Threading`, `System.Threading.Tasks`.
- Types (classes, records, structs) and local functions go AFTER the top-level statements.
- `answer` is the exact output, lines separated by `\n`. Comparison is case-sensitive (C# prints `True`/`False`);
  trailing whitespace and trailing newlines are ignored.
- The program must finish normally. If the point is an exception, catch it and print something
  (e.g. `catch (InvalidOperationException) { Console.WriteLine("Exception"); }`). Unhandled exceptions fail verification.
- Output must be **deterministic**: no `Random` without a seed, no timing races, no `DateTime.Now`, no
  `GetHashCode()` values, no unordered `HashSet`/`Dictionary` enumeration you're relying on, no thread-ordering
  races. Culture is invariant (`1.5`, not `1,5`).
- Keep snippets short (≤ 20 lines). One concept per snippet.
- Distractors are outputs from a plausible *misconception* (e.g. thinking structs are copied by reference).
  `"Compile error"` or `"Throws InvalidOperationException"` are fine as distractors when plausible.
- **The test suite compiles and runs every snippet and fails if the output doesn't match `answer`, or if a
  distractor matches.** If you're unsure what something prints, the test is the source of truth: fix the
  answer, not the test.

### `pick-the-code`
"Which code correctly does X?" The `answer` and `distractors` are code snippets.
- Snippets need not be complete programs; they are not executed.
- Distractors should be *subtly* wrong (sequential instead of concurrent, off-by-one, wrong overload,
  O(n²) when asked for efficient), not obviously broken syntax.
- Typed recall defaults to self-graded, so no need to set `recall`.

### `predict-result` (SQL)
`setup` creates and fills small tables; `code` is a query; what does it return? The app shows the tables as
grids, and after answering shows the real result and highlights which rows affected it.
- **Dialect is SQLite** (in-memory). Joins, CTEs, window functions, GROUP BY/HAVING, UNION/INTERSECT/EXCEPT,
  NULL semantics and subqueries all behave like SQL Server/PostgreSQL. Don't use `TOP`, `ISNULL`, `GETDATE()`,
  `NOLOCK` or other engine-specific syntax: write those as `concept` questions instead.
- Keep tables tiny (2-6 rows, 2-4 columns) and reuse a familiar shape (Customers/Orders, Employees with ManagerId)
  so the user reads the data, not the schema. Use `INTEGER PRIMARY KEY` ids so rows are easy to refer to.
- `answer`: one row per line, values separated by `, `, `NULL` for nulls, `(no rows)` for an empty result.
  No header row. Reals print shortest form (`4`, `2.5`). Grading ignores case, spacing, quotes and blank lines,
  but not row order.
- **Multi-row answers need `ORDER BY`** (the verifier enforces it), because SQL doesn't guarantee row order.
- For "how many rows?" questions set `"expect": "row-count"` and make `answer` the number; no ORDER BY needed.
- **Index / query-plan questions**: set `"expect": "table-access"`. `setup` adds `CREATE INDEX` statements (the app
  lists each table's primary key and indexes under its grid). The answer and distractors must come from this
  vocabulary, which the verifier checks against SQLite's `EXPLAIN QUERY PLAN`: `Full table scan`, `Full index scan`,
  `Covering index scan`, `Index seek`, `Covering index seek`, `Primary key seek`. After answering, the app shows the plan.
  - If the query reads more than one table, set `"planTable"` to the name the plan uses: **the alias** if the
    query has one (`"o"` for `Orders o`).
  - Don't guess plans: the optimiser can surprise you (e.g. join order flips depending on the WHERE clause, or
    `SELECT *` on a table whose columns are all in an index is "covering"). Write the question, run validate, and
    rewrite the question if the real plan isn't the one you meant to teach.
  - SQLite has no statistics here, so it uses an index whenever it can. Don't write questions about selectivity,
    parameter sniffing, key lookups vs scans by cost, or `LIKE 'abc%'` seeks (SQLite's case-insensitive LIKE won't
    seek a normal index). Those stay as `concept` questions.
  - Good topics: functions on columns (sargability), leading wildcards, composite index column order, covering
    vs non-covering, expression indexes, indexing foreign keys for joins, primary-key lookups.
- The best questions are the classic traps where seeing the rows helps: LEFT JOIN + WHERE on the right table,
  `NOT IN` with a NULL, `COUNT(*)` vs `COUNT(col)`, join fan-out inflating SUM, `<>` excluding NULLs.
- Distractors are results from a specific misconception (inner instead of left join, filtering before grouping).
- **The test suite runs every query and fails if `answer` doesn't match, a distractor matches, or the SQL errors.**

## Difficulty scale

1. Junior fundamentals anyone using C# daily knows (value vs reference, `string` immutability).
2. Solid working knowledge (LINQ basics, `out` vs `ref`, common collections and their Big-O).
3. Mid-level / interview staples (deferred execution, async ordering, `new` vs `override`, deadlocks).
4. Senior: subtle runtime behaviour (initialisation order, `ConfigureAwait`, GC generations, `Span<T>`).
5. Expert / obscure edge cases. Use sparingly.

Aim for a spread weighted to 2-3 in every batch.

## Quality rules

- **Correctness over volume.** Don't invent APIs. Target modern C# (.NET 8+, C# 12) and say so in the
  explanation if behaviour changed between versions (e.g. default interface methods in C# 8).
- Distractors must be plausible to someone with a specific misconception, never joke answers.
  Distractors must not be correct under any reasonable reading.
- The prompt must make sense *without* the options (typed mode hides them). Avoid "Which of these...".
- Don't duplicate an existing question's core idea. Check the topic file first; a different angle on the
  same concept (concept vs predict-output) is fine and encouraged.
- Use British/Australian or US spelling consistently within a question; no need to be strict across questions.

## Workflow for generating a batch

1. Read the existing topic file(s) to find the next id and avoid duplicates.
2. Write the questions.
3. Run `dotnet run --project src/Quizzler.Cli -- validate` (or `dotnet test --filter ContentBankTests`).
4. Fix failures. For predict-output mismatches, the message shows what the code actually printed.
   Decide whether the answer key or the snippet is wrong, and re-check the explanation still matches.
5. Report how many questions were added per topic and difficulty, and remind the user to run
   `quizzler import` (don't import into their real database yourself unless asked).
